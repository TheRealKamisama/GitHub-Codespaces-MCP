# M1 首个切片：精确提交任务 / Exact-Revision Jobs (Slice 1)

日期：2026-10-14。状态：**未发布源码实现**；本地、模拟、Linux 容器检查与一轮真实 Codespaces 验证已通过（见下文，仍有未验证项）。这只是 M1 的第一部分：产物、自动导出、本地回收控制进程、实例租约与自动停止仍未实现，因此 **M1 闭环尚未完成**。M0 的传输、绑定与 prepare 行为见 [M0.md](M0.md)，本文只描述新增部分。

## 新增工具

| 工具 | 行为 |
|---|---|
| `project_inspect` | 只读检查本地 Git：HEAD、分支、上游 remote/ref、push URL 解析出的 GitHub 仓库（不返回 URL 和凭据）、已跟踪/未跟踪改动计数、HEAD 是否已包含在上游跟踪 ref 中。仅当 HEAD 已推送时给出 `suggestedSource`。不 commit、push 或 fetch；使用 `core.fsmonitor=false` 避免不可信仓库配置的钩子执行 |
| `job_submit` | 先在本机持久化 job 记录，再提交到绑定的 Available Codespace。远端在受管缓存中 fetch 指定 ref、确认完整 SHA 可从该 ref 到达，在新的 detached worktree 中按顺序执行步骤 |
| `job_get` | 远端状态、每步结果和 execution/verification/cleanup 汇总；`waitSeconds` ≤ 20 等待 settled |
| `job_logs` | 从 `v1:<offset>` 游标读取一页合并日志（默认 32 KiB，最大 256 KiB），不拆分 UTF-8 字符 |
| `job_cancel` | 请求取消；只有步骤进程组被确认退出后 `job_get` 才显示 `cancelled`，否则 `cancel_requested` + `CANCEL_UNCONFIRMED`。`cancelled` 不覆盖进程组外资源（daemon 管理的容器、`nohup`/`setsid` 进程等），这些由 cleanup 步骤处理 |

`job_submit` 与 `job_cancel` 标记 `destructiveHint`：步骤是任意用户命令，MCP 不把它们变成安全沙箱。

## 任务模型

- 来源：仅 `revision` 模式。`source.ref` 必须是完整 `refs/heads/...` 或 `refs/tags/...`，`source.commit` 必须是 40 位 SHA。仓库取自绑定，不能由请求替换。分支前进后仍可执行已推送的祖先提交；不可达时 `REVISION_UNREACHABLE`，**绝不改测分支最新提交**。含 gitlink（submodule）或 LFS 属性的提交分别以 `SUBMODULES_UNSUPPORTED` / `LFS_UNSUPPORTED` 拒绝，不会把指针文件当成真实输入。
- 步骤：最多 32 步，`kind` 为 `command`（argv，不经 shell）或 `shell`（`bash`/`sh`，脚本写成文件后执行，从不拼进 SSH 命令）。字段：`id`、`role`（setup/build/test/analysis/cleanup）、相对 `cwd`、可选 `timeoutSeconds`、`env`、`optional`。任务总期限 `timeoutSeconds` 默认 3600，最大 21600，从 running 开始计算。
- 执行：每步独立进程组、stdin 为空；步骤环境移除 `GH_TOKEN`/`GITHUB_TOKEN` 等，另提供 `CODESPACE_MCP_JOB_ID`、`CODESPACE_MCP_SOURCE_DIR`、`CODESPACE_MCP_STEP_ID`。普通步骤退出后残留的后台子进程会被结束。非 optional 步骤失败后其余普通步骤为 `not_run`；`cleanup` 步骤在成功、失败、超时、取消后都会执行（默认各 300 秒）。清理失败单独记录为 `CLEANUP_FAILED`，不覆盖主失败原因。
- 汇总：`execution` 为 PASS/FAIL/NOT_RUN/INCOMPLETE；`verification` 只看非 optional 的 `test` 步骤：没有则 `NOT_CONFIGURED`，全部通过才 `PASS`，未执行为 `NOT_RUN`；`cleanup` 同理。`sourceModified` 记录步骤是否修改了已跟踪源码。
- 状态：`accepted → preparing → queued → running → succeeded / failed / timed_out`，以及 `cancel_requested → cancelled` 和 `interrupted`。`settled=true` 表示不会再变化。`observation` 为 `reachable` 或 `stale`（心跳超过 10 秒但 supervisor 仍存活）。generation 改变为 `JOB_INTERRUPTED`；supervisor 已消失且心跳过期为 `SUPERVISOR_LOST`。中断的任务不会被自动重跑。
- 进程组外资源：runner 只管理步骤进程组。任务若创建容器等外部资源，应使用 `CODESPACE_MCP_JOB_ID` 打标签并在 `cleanup` 步骤中按标签清理（示例见设计文档 §7.3、§9.1）；MCP 不内置 Docker 或其他工具链的专用逻辑。
- 并发：每个项目根目录一个运行槽（flock），其余任务 `queued`；排队时间不计入任务期限，目前没有独立排队期限。

## 幂等与恢复

- `jobId = sha256(账号, 仓库, projectId, requestId)`；计划摘要包含 projectId、仓库、实例、远端根目录、source、steps 和期限，不包含 locale。同 requestId 不同计划在本地和远端都返回 `IDEMPOTENCY_CONFLICT`。
- 本机记录的 `submission`：`pending`（已持久化，正在发送）、`not_sent`（在连接前失败，确定未执行，可用同 requestId 重试）、`accepted`、`unknown`（发送后结果不明，**必须用同 requestId 对账**）、`rejected`。已是 `unknown`/`accepted` 的记录不会被降级为 `not_sent`。
- `job_get`/`job_cancel` 成功观测后把本机记录更新为 accepted 并缓存最新状态；本机状态锁忙时跳过缓存，不阻塞观测。丢失本机记录时仍可用绑定和 jobId 查询远端。绑定改到其他实例或根目录后，旧任务返回 `JOB_LOCATION_CHANGED`，不会迁移。
- 远端状态文件只有 supervisor 一个写入者；取消仅写入标记文件，读取时再计算 interrupted/stale，避免竞争写入。

## 远端布局

```text
<remoteProjectRoot>/
  .codespace-mcp/
    owner.json, runner/<build>/          # M0
    cache.git/                           # 受管 bare 缓存；refs/codespace-mcp/jobs/<jobId> 固定每个任务的提交
    jobs/<jobId>/request.json status.json supervisor.json cancel.json job.log steps/
  runs/<jobId>/src/                      # 该任务的 detached worktree
```

源码 fetch 使用 `https://github.com/<repository>.git` 和 Codespace 内已有的 git 凭据；supervisor 保留凭据环境用于 fetch，步骤进程不继承 token。日志总量上限 64 MiB，超出时结束当前步骤并记 `OUTPUT_LIMIT`。worktree、日志和缓存目前**没有保留期清理**。

## English

Slice 1 of M1 adds `project_inspect` (read-only local Git inspection) and asynchronous exact-revision jobs: `job_submit`, `job_get`, `job_logs`, `job_cancel`. The runner fetches the named ref on the bound Codespace, verifies that the full commit is reachable from it (never substituting the branch tip), rejects submodules and LFS, and runs ordered command/shell steps in a fresh detached worktree. Each step gets its own process group and a token-free environment. Cleanup steps always run. Results report execution, verification and cleanup separately, and verification is PASS only when every required test step passed. Submission is persisted locally before the remote call. A lost response is reconciled by reusing the same requestId, and a different plan under the same requestId is refused. Cancellation reports `cancelled` only after the step process groups are verified gone. That does not cover resources outside them, such as daemon-managed containers; jobs tag those with `CODESPACE_MCP_JOB_ID` and remove them in cleanup steps. There is deliberately no Docker-specific step type.

Evidence: Linux Node 24 checks, local simulations, real local Git for inspection, Linux container runs, and a live run on a real Codespace created in this repository (2026-10-14) driven through the real MCP stdio server. Live PASS: prepare, probe survival across SSH sessions and MCP restarts, private fetch with the Codespace's own credentials, exact-commit jobs, this project's own CI as a job, the runnable demos plus node-ci, Docker build/test and a Postgres container through ordinary steps, cancellation with label-based cleanup, queueing, and stop/restart reported as interrupted without re-running. The live run found and fixed two bugs: missing platform variables in non-login SSH sessions, and stale step/summary data for interrupted jobs. Still not verified live: mid-call SSH loss, a branch advancing after submit, Windows/macOS clients. Artifacts, automatic export/stop, leases and retention cleanup are not implemented. M1 is not complete until automatic release passes live acceptance.
